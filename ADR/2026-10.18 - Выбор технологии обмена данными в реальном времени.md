
**ADR: 2026-10.15 - Выбор технологии обмена данными в реальном времени**

**Дата:** 21 октября 2026 г.

**Статус:** Принято

**Контекст:**

В приложении EduRate необходимо предусмотреть механизм обмена данными в реальном времени между серверной частью и клиентскими приложениями.

Он необходим для оперативного информирования пользователей о событиях, происходящих в системе, без необходимости вручную обновлять экран или повторно отправлять запросы к серверу.

К таким событиям относятся изменение статуса отзыва после проверки модератором, получение новых уведомлений и другие изменения, связанные с использованием приложения.

Серверная часть EduRate разрабатывается на Python с использованием Django и Django REST Framework, а клиентская часть — на Flutter.

Необходимо выбрать технологию, которая обеспечит двустороннее или серверное взаимодействие в реальном времени, будет поддерживать интеграцию с существующим технологическим стеком и позволит в дальнейшем увеличивать количество одновременных подключений.

При выборе решения важно учитывать возможность самостоятельного развёртывания, простоту интеграции, наличие клиентских библиотек для Flutter и разграничение доступа пользователей к получаемым событиям.

**Рассмотренные варианты:**

1. **Centrifugo:** отдельный сервер обмена сообщениями в реальном времени с поддержкой WebSocket, HTTP-streaming, Server-Sent Events и других транспортов. Использует модель публикации и подписки (Pub/Sub), позволяющую клиентам подписываться на каналы и получать сообщения. Серверная часть может отправлять события через HTTP API.
2. **Django Channels:** расширение Django, обеспечивающее обработку WebSocket-соединений и других протоколов на основе ASGI. Позволяет реализовать обмен сообщениями непосредственно в серверном приложении с использованием потребителей (Consumers) и каналов.
3. **Socket.IO:** библиотека для организации двустороннего обмена событиями в реальном времени. Поддерживает переподключение клиентов, комнаты и механизмы передачи сообщений. Для интеграции с Django потребуется отдельная настройка серверной части.
4. **Ably:** облачная платформа обмена сообщениями в реальном времени. Предоставляет готовую инфраструктуру для передачи событий между серверной частью и клиентами, включая механизмы каналов и управления подключениями.
**Решение:**

Выбран Centrifugo в качестве отдельного сервера обмена данными в реальном времени с использованием протокола WebSocket.

**Обоснование:**
- **Разделение ответственности:** бизнес-логика остаётся в Django, а обработка постоянных соединений и доставка сообщений выполняются отдельным сервером Centrifugo. 
- **Интеграция с Flutter:** для Centrifugo существует клиентская библиотека для Dart/Flutter, позволяющая подключаться к серверу, подписываться на каналы и получать сообщения. 
- **Интеграция с Django:** серверная часть может отправлять сообщения через HTTP API, не требуя непосредственной реализации WebSocket-соединений в Django. 
- **Поддержка каналов:** модель Pub/Sub позволяет разделять сообщения по пользователям и типам событий, предоставляя каждому клиенту только необходимые обновления. 
- **Масштабируемость:** Centrifugo поддерживает горизонтальное масштабирование и работу нескольких экземпляров сервера. 
- **Автоматическое переподключение:** клиентские библиотеки поддерживают восстановление соединений и подписок после временных проблем с сетью. 
- **Возможность расширения:** при появлении новых функций можно добавлять каналы для уведомлений, обновлений отзывов и других событий без существенного изменения основной архитектуры. 
- **Самостоятельное развёртывание:** Centrifugo можно развернуть в собственной инфраструктуре, не передавая обработку сообщений стороннему облачному поставщику.

**Последствия:**

- Необходимо развернуть и настроить сервер Centrifugo в инфраструктуре EduRate.
- Следует настроить взаимодействие Django с Centrifugo через HTTP API.
- Необходимо подключить клиентскую библиотеку Centrifugo для Dart/Flutter.
- Серверная часть должна формировать события и отправлять их в соответствующие каналы после выполнения бизнес-операций.
- Следует предусмотреть отдельные каналы для пользовательских уведомлений и других событий системы.
- Необходимо реализовать выдачу клиентам токенов подключения с ограниченным сроком действия.
- Права на подписку к каналам должны определяться серверной частью с учётом роли и идентификатора пользователя.
- Клиентское приложение должно обрабатывать потерю соединения, повторное подключение и восстановление подписок.
- Для получения актуального состояния после длительного отсутствия соединения приложение должно иметь возможность повторно запросить данные через REST API.
- Необходимо предусмотреть журналирование ошибок взаимодействия и мониторинг доступности Centrifugo.
- При передаче событий не следует включать избыточные персональные данные. Клиент должен получать только информацию, необходимую для отображения соответствующего обновления.
