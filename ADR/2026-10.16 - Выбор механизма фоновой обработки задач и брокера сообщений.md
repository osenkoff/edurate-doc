
**ADR: 2026-10.15 - Выбор механизма фоновой обработки задач и брокера сообщений**

**Дата:** 21 октября 2026 г.

**Статус:** Принято

**Контекст:**

В приложении EduRate необходимо предусмотреть механизм фоновой обработки задач, которые не должны выполняться непосредственно во время обработки пользовательских HTTP-запросов.

К таким задачам относятся отправка электронных писем, отправка push-уведомлений, обработка загруженных документов, выполнение периодических операций и другие действия, которые могут занимать дополнительное время.

Выполнение подобных операций непосредственно в обработчиках запросов может увеличивать время ожидания ответа и снижать отзывчивость приложения.

Необходимо выбрать решение, которое позволит выполнять фоновые задачи независимо от основной серверной части, обеспечит интеграцию с Django и будет соответствовать предполагаемому масштабу проекта.

На начальном этапе EduRate не предполагается высокая нагрузка, обработка больших потоков событий или сложная распределённая архитектура. При выборе необходимо учитывать, что система выполнения фоновых задач и брокер сообщений выполняют разные функции: первая отвечает за запуск и обработку задач, второй — за передачу задач рабочим процессам.

**Рассмотренные варианты:**

1. **Celery + Redis:** Celery использется для организации и выполнения фоновых задач, а Redis выступает брокером сообщений, передающим задачи рабочим процессам. Решение поддерживает асинхронное выполнение, повторные попытки и планирование переодических операций. 
2. **Celery + RabbiMQ:** Celery используется для выполнения фоновых задач, а RabbitMQ — в качестве отдельного брокера сообщений. RabbitMQ предоставляет механизмы управления очередями, маршрутизации сообщений и подтверждения их обработки.
3. **Apache Kafka:** распределённая платформа потоковой обработки событий, предназначенная для передачи, хранения и обработки больших объёмов сообщений. Для выполнения фоновых задач потребуется разработать или использовать отдельные обработчики сообщений.

**Решение:**

Выбран Celery + Redis.

**Обоснование:**

- **Соответсвие масштабу проекта:** для EduRate не предполагается высокая нагрузка и обработка больших потоков событий. Возможностей Celery и Redis достаточно для выполнения предусмотренных фоновых операций.
- **Интеграция с Django:** Celery поддерживает интеграцию с Python-приложениями и позволяет выносить длительные операции из обработчиков HTTP-запросов.
- **Простота разработки:** фоновые задачи описываются в виде отдельных Python-функций, которые могут выполняться независимо от пользовательских запросов.
- **Небольшая сложность инфраструктуры:** использование Redis в качестве брокера позволяет не разворачивать дополнительный специализированный брокер сообщений. 
- **Поддержка повторных попыток:** Celery позволяет настраивать повторное выполнение задач при возникновении временных ошибок.
- **Периодические задачи:** Celery Beat позволяет планировать регулярные операции, например очистку устаревших данных и выполнение фоновых проверок.
- **Возможность масштабирования:** при увеличении количества задач можно запускать дополнительные рабочие процессы Celery Worker.
- **Использование Redis в других компонентах:** Redis уже выбран для кэширования данных EduRate, что позволяет использовать знакомую технологию в нескольких частях инфраструктуры.

**Последствия:**

- Необходимо интегрировать Celery с серверной частью EduRate на Django.
- Следует выносить длительные и независимые операции в отдельные фоновые задачи.
- Для выполнения задач необходимо настроить отдельные рабочие процессы Celery Worker.
- Redis должен использоваться в качестве брокера сообщений для передачи задач от серверной части к рабочим процессам.
- Необходимо предусмотреть логическое или инфраструктурное разделение Redis для кэширования и обработки очередей. Для рабочей эксплуатации предпочтительно использовать отдельные экземпляры Redis, чтобы политика очистки кэша не влияла на очередь задач.
- Следует настроить параметры сохранности данных брокера и ограничения использования памяти. 
- Для периодических операций необходимо настроить Celery Beat. 
- Следует предусмотреть обработку ошибок и настройку повторных попыток выполнения задач. 
- Для операций, которые могут выполняться повторно, необходимо обеспечить идемпотентность, чтобы избежать дублирования действий. 
- Необходимо вести журналирование результатов выполнения фоновых задач и контролировать состояние очередей и рабочих процессов. 
- При существенном увеличении нагрузки следует повторно оценить возможности выбранного брокера и рассмотреть переход на RabbitMQ.
