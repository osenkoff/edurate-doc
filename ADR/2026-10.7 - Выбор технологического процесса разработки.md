
**ADR: 2026-10.7 - Выбор технологического процесса разработки**

**Дата:** 21 октября 2026 г.

**Статус:** Предложено

**Контекст:**

Для разработки EduRate необходимо выбрать технологический процесс, обеспечивающий управляемое выполнение задач, контроль качества, возможность адаптации требований и регулярную поставку работающих версий продукта.

EduRate включает мобильное приложение на Flutter, серверную часть на Python с использованием Django REST Framework и базу данных PostgreSQL. Проект предполагает реализацию каталога образовательных организаций, поиска и сравнения программ, рейтингов преподавателей, отзывов пользователей, механизмов подтверждения обучения и модерации.

Поскольку требования и приоритеты могут меняться по мере развития продукта, необходимо организовать разработку так, чтобы новые функции можно было выпускать поэтапно, а ошибки выявлять на ранних стадиях.

**Рассмотренные варианты:**

1. **Waterfall:** последовательная разработка по заранее определённым этапам.
2. **Scrum:** итеративная разработка короткими спринтами с регулярным планированием и анализом результатов.
3. **Kanban:** непрерывное выполнение задач с визуализацией рабочего процесса и ограничением незавершённой работы.

**Решение:**

Выбран Agile-подход с использованием Scrum.

Разработка будет организована через последовательное выполнение приоритетных задач из продуктового бэклога. В рамках каждого спринта команда планирует объём работ, реализует функциональность, проводит тестирование и демонстрирует полученный результат.

**Обоснование:**

- **Гибкость требований.** Приоритеты функций можно корректировать на основе обратной связи и результатов тестирования.
- **Постепенная поставка продукта.** Функциональность EduRate можно реализовывать поэтапно, начиная с минимально жизнеспособного продукта (MVP).
- **Регулярный контроль качества.** Автоматические тесты и проверка кода позволяют выявлять ошибки до выпуска изменений.
- **Прозрачность процесса.** Бэклог и задачи спринта позволяют отслеживать прогресс и выявлять препятствия.
- **Непрерывное улучшение.** Ретроспективы помогают совершенствовать процесс разработки после каждого спринта.

**Последствия:**

- Требования и задачи будут храниться в продуктовом бэклоге.
- Перед началом спринта будут определяться приоритеты и план работ.
- Каждое изменение кода должно проходить проверку и соответствующие автоматические тесты.
- Для управления версиями и совместной разработки будет использоваться Git.
- Для контроля изменений будут применяться Pull Request и Code Review.
- Автоматизированные проверки будут запускаться через CI при внесении изменений.
- По завершении спринта будет оцениваться реализованная функциональность и собираться обратная связь.
- Команда будет регулярно проводить ретроспективы и корректировать процесс при необходимости.
